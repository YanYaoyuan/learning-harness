# Agent 研究选题调研与复现实验路线

> 本文保留为首轮调研记录。用户补充可使用 API，并要求提高研究问题层次后，当前建议已更新为 [研究议题 V2](RESEARCH_AGENDA_V2.zh-CN.md)，优先考虑学习型 harness 和可迁移的自改进算子。

调研截止：2026-11-09。资源：同机 4×A100 40GB，另有 2×RTX 5090。目标：论文选题与可复现实验路线。

本报告依据原始论文页面及与选题最相关的方法描述，整理研究关系、近邻工作和实验建议。论文 PDF 已按指定版本收集；本次没有运行作者实验。可行性与选题排序是研究判断，候选题的新颖性仍需进一步逐篇核查。

## 1. 建议选择的主线

**优先研究：小模型 Agent 在变化的工具环境中，如何持续维护可复用的组合技能，并在有限验证预算下减少错误复用和遗忘。**

这里五个兴趣点可以各自承担一个明确角色：

- 小模型是实际执行、规划和调用工具的主策略。
- Harness 提供交互循环、上下文管理、技能读取、验证和错误恢复。
- Continual learning 规定任务以流的形式到达，既要适应变化，也要保留仍然有效的旧能力。
- Agentic RL 用于学习“复用、探测、修复、隔离”这些决策；是否需要 RL 由强启发式对照决定。
- RSI 是后续扩展：让系统改进自己的更新规则，并检验下一轮改进效率。首篇工作可以先聚焦持续学习机制。

这条主线适合你的资源，因为主要实验可以在 4B 级模型和本地可验证环境中完成。最初两周应优先验证失效机制和强基线之间是否存在空间。

## 2. 五个方向之间的关系

为方便讨论，将 Agent 写作 A=(πθ,H,M,S)：πθ 是模型策略，H 是控制与交互机制，M 是经验记忆，S 是可执行或文本形式的技能。实际实现中 M、S 往往属于广义 harness。

| 方向 | 主要改变什么 | 有说服力的证据 | 常见误判 |
|---|---|---|---|
| Harness optimization | prompt、工具接口、循环、上下文与终止规则 | 固定模型与预算，未见任务上获得收益 | 把更多重试或更长上下文的收益归因于机制 |
| RSI | 当前 Agent，进一步包括产生下一轮改进的机制 | 相同总预算下，后续改进效率提高且有迁移 | 只报告一次最终分数，无法区分搜索、选择和递归收益 |
| Continual learning | 权重或跨任务保留的外部状态 | 先测后学、适应速度、旧能力保持、跨任务迁移 | 有记忆文件就宣称持续学习 |
| Small-model agents | 让小模型承担核心决策 | 单次成功率、长程可靠性、成本与失败恢复 | 用大模型完成全部规划，只让小模型执行；或以 pass@64 代替 pass@1 |
| Agentic RL | 从多轮环境交互中更新策略 | 未见环境收益、有效探索、稳定训练、可验证结果 | 将单轮答案 RL 的增益直接外推到长程 Agent |

小模型、harness 和训练分布存在耦合。已有工作报告：在演化后的 harness 上，直接模仿强模型整条轨迹可能使弱模型退步；基于弱模型自身 rollout 的局部纠正更合适。见 [On-Policy Correction](https://arxiv.org/abs/2609.09134)。

## 3. 研究进展与必须排查的近邻

### 3.1 Harness 与 RSI

- [GEPA](https://arxiv.org/abs/2507.19457)：利用完整轨迹中的语言反馈反思和搜索 prompt。适合作为不更新权重的基础对照。
- [DGM](https://arxiv.org/abs/2505.22954)：通过自修改代码和候选档案积累能力。阅读时关注演化档案、候选选择、运行成本和泛化。
- [RHI](https://arxiv.org/abs/2607.15524)：以 prompt 级 agent-loop 规范优化 harness，强调信息流与上下文管理。
- [ModularRSI](https://arxiv.org/abs/2609.14857)：模块化、成功/失败轨迹对比和与评测集分离的演化任务。单纯“拆模块再演化”已有直接近邻。
- [RRSI](https://arxiv.org/abs/2609.24972v3)：对候选提议、筛选和裁剪加约束，减少 benchmark 特化并控制运行成本。本文固定下载 v3，避免混用早期版本结果。
- [Hyperagents](https://arxiv.org/abs/2603.19461v2)：将任务 Agent 和可自修改的 meta agent 放入同一可编辑程序，直接讨论改进机制自身的改进。
- [Does Failure Feedback Direct Agent Self-Modification?](https://arxiv.org/abs/2610.14662)：指出选择后的总体提升不能单独证明反馈导致了定向修复；目标修复与 held-out 增益需要分开报告。

**判断：** 用固定大模型优化 prompt、memory 或工具，再报告少数 benchmark 涨分，已经需要很强的额外贡献。更有价值的证据在于迁移、归因、成本，以及跨轮次能力保持。

### 3.2 持续学习与记忆/技能

- [ACE](https://arxiv.org/abs/2510.04618)：以增量 playbook 积累策略，关注反复压缩和重写导致的信息流失。
- [LifelongAgentBench](https://arxiv.org/abs/2505.11942)：包含 DB、OS、KG 三类可自动验证的交互环境，是合适的复现入口。
- [LifeSkill](https://arxiv.org/abs/2606.04815)：用 verifier 评价技能的实际效用，并通过在线更新将技能相关行为内化到策略参数。“外部技能 + 参数内化”已有工作。
- [HCL](https://arxiv.org/abs/2608.19013)：明确讨论 harness-level forgetting，并用改进、历史保持与有效性检查控制状态提交。“更新前加历史回归门控”已有工作。
- [ReHarness](https://arxiv.org/abs/2610.12668)：严格在线条件下，利用当前轨迹回溯修订已检索经验，处理过度泛化和过时知识。
- [Are Self-Evolving Agents Continual Learners?](https://arxiv.org/abs/2610.25858)：在 BIRD、BFCL、ScienceWorld 构建的漂移任务流上，分析全局修改干扰、覆盖旧知识和检索冲突。
- [STALE](https://arxiv.org/abs/2605.06527)：研究隐式新证据如何使旧记忆失效，以及识别失效和实际行动之间的差距。
- [ERRAND](https://arxiv.org/abs/2609.29545)：将重验证作为竞争同一行动预算的维护动作。因此“何时花成本重查旧知识”本身已有直接先例。
- [SkillCommit](https://arxiv.org/abs/2608.15165v2)：保留实例 patch，通过跨实例回放和机制检查扩展技能适用范围。因此“给技能增加回放验证”也不足以单独形成贡献。
- [Continual AutoResearch](https://arxiv.org/abs/2611.05108)：持久状态可能提升研究效率，但未必稳定改善最终解质量。这支持分别测量适应速度与最终性能。

**判断：** 需要把“检索到相关经历”“保持正确状态”“可靠地复用流程”分别测量。外部状态也会遗忘和产生干扰，冻结权重不能消除这个问题。

### 3.3 小模型 Agent 与 agentic RL

- [AgentCPM-Explore](https://arxiv.org/abs/2602.06485)：4B 主模型的直接参考，讨论 SFT 遗忘、奖励噪声与长上下文冗余。其摘要中突出报告的 GAIA 文本任务结果包含 pass@64 条件，不能作为单次成功率对照。
- [Small Language Models are the Future of Agentic AI](https://arxiv.org/abs/2506.02153)：提供小模型适用性的论证和架构视角；具体场景仍应以相同任务和成本下的实验为依据。
- [RAGEN-2](https://arxiv.org/abs/2604.06268)：多轮 RL 可能出现输入无关的模板推理，即使 entropy 看起来稳定。应同时关注输入依赖性、奖励方差和实际交互行为。
- [Agent Lightning v1.0](https://arxiv.org/abs/2608.17528)：实际运行 harness 直接参与 RL，讨论 retokenization、样本合并、advantage 和 loss normalization 等问题。官方复现代码可作为训练接入参考。

多轮 Agent 的额外难点包括长程信用分配、工具观察不计入策略生成损失、历史压缩后 token 前缀变化、环境耗时与奖励可利用性。选择 RL 框架时，应先核查它是否正确处理你的真实 harness 轨迹。

### 3.4 Model-harness 共演化

已经出现 [HELIX](https://arxiv.org/abs/2608.13951)、[VACE](https://arxiv.org/abs/2609.37105)、[On-Policy Correction](https://arxiv.org/abs/2609.09134)、[CoHARL](https://arxiv.org/abs/2610.36469)。其中 VACE 研究带验证门控的交替更新，CoHARL 研究共享策略与可执行 harness 群体的共同演化。

**判断：** “先优化 harness，再 RL，然后循环”已经有直接竞争工作。若研究这条路线，需要围绕一个明确机制，例如小模型与新 harness 的兼容性、跨环境保持或训练成本，提出可证伪假设。

## 4. 算力对应的现实实验范围

以下是工程估计，尚未在你的机器实测。

| 用途 | 建议范围 | 资源安排 |
|---|---|---|
| 快速失败分析、harness/技能基线 | 1.7B–4B | 5090 分别运行独立推理 worker |
| 主实验 SFT / LoRA 多轮 RL | 4B | 同机 4×A100 40GB |
| 模型规模扩展 | 7B–8B，以 LoRA 和较短上下文优先 | 先测峰值显存与吞吐，再确定批量 |
| 4B 全参数 RL | 可做受控试验 | 需分片、较短序列、控制 actor/reference/rollout 驻留 |
| 14B+ | 选择性推理对照 | 不作为首轮长程训练主力 |

RTX 5090 参考规格为每卡 32GB，且不支持 NVLink，见 [NVIDIA 官方规格](https://www.nvidia.com/en-us/geforce/graphics-cards/50-series/rtx-5090/)。两张卡适合独立 rollout 或评估服务。4 张 A100 的物理总显存是 160GB，能否高效分片仍取决于实际互联；需要用 nvidia-smi topo -m 核查，不能将同机等同于高速全互联。

BF16 权重的粗略占用：4B 约 8GB，8B 约 16GB。常规混合精度 Adam 全量训练状态按约 16 bytes/parameter 估算，分别约 64GB 和 128GB；这还没有包括激活、KV cache、参考模型和 rollout 引擎。具体实现会改变这一估计。LoRA 减少可训练状态，但长序列的激活和生成缓存仍然存在。

初始配置建议：4B、4K–8K 最大输入上下文、每次模型调用最多 256–512 新 token、每任务最多 8–16 次交互、每训练任务采样 4 条轨迹。先运行 100 个 episode 记录真实分布，之后再增加长度和并发。这些数值是起点，需根据任务可解性调整。

可采用 [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) 作为结构简单且公开的主模型，固定模型 revision 与工具模板。AgentCPM-Explore 可作为同量级的专业 Agent 对照；因其训练数据和系统配置不同，应明确作为跨模型参考。

软件尽量采用单一训练栈：[Agent Lightning](https://github.com/microsoft/agent-lightning) 或其支持的训练后端择一打通。可参考 [AgentCPM](https://github.com/OpenBMB/AgentCPM) 的训练/沙箱/评估组合；原论文完整训练资源不应默认等同于你能完整复现的资源。

## 5. 三个候选题与优先级

### A. 首选：工具变化下，组合技能的依赖感知维护

暂定英文描述：Dependency-Aware Maintenance of Compositional Skills for Small Language Model Agents。

**研究问题：** 一个底层工具或环境假设变化时，Agent 能否定位哪些组合技能受影响，只检查必要的依赖，并保留仍有效的其他技能？

例子：技能“查价格→换算币种→生成报表”与“报销核验→换算币种→写账本”共用换算步骤。工具输出单位发生变化后，单纯按用户问题检索旧流程可能继续误用；逐条重跑整个技能库则消耗过多预算。

候选方法：从实际调用轨迹抽取技能使用的工具、前置条件和中间结果假设；保留可观察证据与最近验证记录；变化证据沿依赖关系标记受影响技能；在同一行动预算内选择探测、局部修复、隔离或直接复用。没有观察证据的工具变化须允许通过诊断调用识别，不能要求模型猜测不可辨识的隐藏状态。

与近邻的差别需要落在**组合技能共享依赖的失效传播与局部维护**上：

- 相对 STALE，评估可执行技能的多步骤行为。
- 相对 ERRAND，检验依赖共享和多技能影响能否改善重验证预算分配。
- 相对 SkillCommit，关注部署后环境变化，而非只扩大已验证实例上的适用范围。
- 相对 HCL / ReHarness，给出可控的工具语义变化与局部干预归因。

这几个差别是候选研究定位。精读后若发现近邻已覆盖同样机制，应缩小问题或转向下面的诊断研究。

**最小实验：** 用 4B 冻结主模型，先实现依赖记录和启发式维护。只有启发式方案在预算分配上仍存在可测差距时，再用 LoRA RL 学习维护决策。

RL 的动作可以包含 USE、PROBE、REPAIR、QUARANTINE；工具实际执行与评分由环境完成。训练可用任务成功与维护成本构造奖励，主要结论应以固定硬预算下的成功率和成本曲线给出，避免依赖单一惩罚系数。

**最大风险：** 改进来自增加元数据或额外调用。需要给启发式与学习策略相同的可用信息、存储和行动预算，才能归因于决策策略。

### B. 备选：小模型持续学习收益的可控诊断与干预

**研究问题：** 在相同模型、总 token、工具次数和可见反馈下，持续状态的增益究竟来自正确经验迁移、额外搜索，还是任务特化？哪些干扰能通过最小局部干预消除？

在已有漂移任务流上，加上可控的组合依赖变化和环境恢复，比较 memory-only、harness-only、weight-only 与组合方案，分别测目标修复、相关技能迁移和不相关技能回归。以错误机制的可干预证据作为核心，再加入一个针对性修复机制。

最近近邻包括 Are Self-Evolving Agents Continual Learners?、HCL、Does Failure Feedback Direct Agent Self-Modification? 与 Continual AutoResearch。仅增加几个模型或重复遗忘曲线贡献有限；应提供新失效机制、真实可复用环境和能排除替代解释的干预。

**资源匹配：** 高，主要消耗本地推理。适合作为 A 的前两周可交付结果，也是训练收益不足时的备选。

### C. 后续高风险题：小模型能否提高自己的改进效率

**研究问题：** 一个小模型改进器积累修改经验后，能否在未见任务族上，用更少的候选和验证次数找到有效 harness 修改？若允许更新改进器自身，这种效率提升是否能跨轮持续？

必须与固定改进器、随机/预定义修改、相同候选数的搜索对照，并分别报告候选命中率、每次验证收益、最终性能和总预算。Hyperagents 和 AIDE² 是关键近邻。

**风险：** 小模型可能还没有足够的代码修改能力；外层评估成本高；一次任务表现提升不能证明改进机制获得递归收益。建议在 A 或 B 建立可重复环境后再做。

## 6. 首选题的具体实验协议

### 6.1 环境与任务流

1. 先复现 [LifelongAgentBench 官方代码](https://github.com/caixd-220529/LifelongAgentBench) 的 DB/OS 子集，确认模型确实具有一定基础任务成功率。
2. 再构建本地、确定性、自动评分的工具环境，组合 2–5 个工具形成任务。任务内容、工具返回及评分逻辑分别保存。
3. 变化类型包括显式 schema 变化、schema 不变的语义变化、共享底层依赖变化、无关工具变化。语义变化必须通过允许的文档、观察或探测调用辨识。
4. 任务流至少包含稳定→变化→稳定，以及 A→B→A 的环境恢复；另加交错环境，用于检验保留旧版本而非永久覆盖的价值。
5. 训练、验证和测试按工具家族、组合模板和变化机制分开，不能只随机拆分同一模板的措辞。保留一个外部 benchmark 作为迁移检查。

先采用每流约 200 个任务、4 个阶段的试验规模；在独立开发集上确定长度和漂移强度后固定。数据规模是实验设计建议，不对应原论文既有规模。

### 6.2 分阶段对照

第一阶段建立基本事实：无持久状态、固定容量近邻检索、ACE 风格增量策略、ReHarness，以及依赖感知启发式。

第二阶段围绕预算与提交机制加入 ERRAND 风格预算维护、SkillCommit 风格回放、HCL 风格提交检查。移植到新环境的版本须逐项说明与原方法的差异；只有运行作者相同设定才称为原结果复现。

第三阶段比较同架构 SFT 与 LoRA RL。再增加两个关键上界/消融：给出真实有效性信息的 oracle（仅作上界），以及给启发式相同依赖信息的对照。

### 6.3 主要指标

- 先测后学的任务流平均成功率和累计成功数。
- 变化后的适应曲线及恢复所需任务数。
- 对先前仍有效任务/环境版本的保持能力与重新遇到时的恢复速度。
- 失效技能误用率、无必要验证率、局部修复后的回归率。
- 每成功任务的生成 token、工具调用、维护调用和墙钟时间。
- 不同总行动预算下的成功率曲线。

使用至少 3 个训练随机种子；任务流顺序也做至少 3 种扰动并独立报告。预算不足时，先在单种子开发实验筛选配置，再对少量主方法完成正式重复。统计区间应以 seed/任务流为单位，避免把同一持续状态下的每个任务误当成独立样本。

### 6.4 必要消融与归因

- 无依赖结构、相同元数据容量的平面技能库。
- 只做语义检索、只做时间/版本筛选、每次验证、从不验证。
- 完整重跑技能与只检查受影响依赖。
- 同信息同预算的启发式、SFT、RL。
- 只维护外部状态与另加定期参数内化，作为后续扩展。

目标任务修好、相关技能变好、无关技能未退步应分别报告。额外搜索、重试和验证都计入预算。最终迁移评测集不参与候选选择；持续学习评估中只允许既定协议的当前反馈写回状态，额外评估探针不写回也不用于选择。

## 7. 六周推进安排与停止条件

| 时间 | 交付与判据 |
|---|---|
| 第 1 周 | 精读最近近邻；跑通 4B 推理和一个 DB/OS 环境；测 100 个 episode 的成功率、长度、显存和吞吐 |
| 第 2 周 | 完成漂移任务流与强启发式；验证组合依赖变化确实造成可重复错误，且简单版本/时间规则无法充分解决 |
| 第 3 周 | 加入依赖感知局部维护；完成同信息、同预算对照，确认收益与机制对应 |
| 第 4 周 | 若预算分配仍有空间，运行 SFT 与 LoRA RL；观察奖励方差、无效调用、输入相关性与坍塌 |
| 第 5 周 | 固定主配置，完成种子、任务顺序、模型规模及外部迁移检查 |
| 第 6 周 | 整理失败案例、统计区间、消融、可复现环境与论文论证 |

六周是推进安排，实际墙钟时间应在第 1 周依据实测吞吐重新估算。不要从显存总量推断训练时长。

停止或转向条件：若简单工具版本规则已解决大多数错误，应研究更真实的语义/共享依赖变化；若依赖信息已让启发式接近 oracle，应优先形成机制研究，无需强行加入 RL；若近邻已覆盖相同组合失效与维护方法，应改题。
